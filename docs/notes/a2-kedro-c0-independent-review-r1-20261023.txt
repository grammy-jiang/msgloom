## P1 – fix before ACCEPT

**P1-1. The doc's source audit is wrong about held-only worksets.**
- Doc line 21 says "Held-only and A2-held cannot be finalized by this old proof." That is false for intake-held-only worksets.
  - `intake_completion.py:252` only raises when `selection_refs` is non-empty.
  - With an empty `refs`, nothing is covered and `completion_receipts` returns no proofs. The status check at `:183-195` is skipped (`if proofs`), and `intake_store.py:348-351` accepts any COMPLETE or INCOMPLETE.
  - So legacy can finalize a held-only workset as COMPLETE.
- Even with selections present, the aggregate status at `:184-195` ignores `workset.held`. COMPLETE with intake-held entries is accepted if every plan is COMPLETE.
- The prototype's rule (held means INCOMPLETE; `c0_contract_prototype.py:337-351`, doc line 126) is therefore a deliberate policy change from legacy, not a restatement.
- Fix: correct the table row, state the policy change, and record the legacy behaviour as a finding for the A1/legacy owner. Do not edit A1.
- Doc §8 "no automatic spin" depends on this.

**P1-2. Three negative tests likely pass for the wrong reason.** I can't run them, so this is high-likelihood, not confirmed.
- Affected: `test_c0_contract_prototype.py:204-211`, `:380-383` and `:400-403`.
- `ResultRef` and `VersionRef` are stdlib frozen dataclasses (`contracts/models.py:55-66`). The models are `strict=True` (`c0_contract_prototype.py:34`). Python-mode `model_dump()` turns the dataclasses into dicts, and strict validation likely rejects those dicts whatever the other fields hold.
- At `:380-383`, `model_copy(update=...)` doesn't validate, and `model_validate` runs on the original dump. The XOR rule (`c0_contract_prototype.py:109`) and the transition-stage rule (`:122-125`) are not actually exercised.
- At `:400-403`, `CompletionReceipt` has no construction-time check for an empty `policy_version`. That check lives only in `validate_against` (`:352`), so a ValidationError there can only come from the strictness artifact.
- This undercuts the doc's "strict frozen payloads" claim (line 27).
- Fix: use `mode="json"` with `model_validate_json`, or pass instances, and test each invariant separately.

**P1-3. The "occurrence vs `selection_refs` dedup" claim is not exercised.**
- The fixture gives every occurrence a distinct ref (`test_c0_contract_prototype.py:69-77`, `i*3+j`).
- The only `selection_refs` check is that it is non-empty (`:271`).
- The workset validator does allow an equal `ResultRef` at different entries (`intake_models.py:227-237`).
- A1's selection identity embeds the entry JSON (`intake.py:205-215`), so A1 can't produce that case. The doc should say so.
- Fix: add a test with an equal `ResultRef` at two entries.

**P1-4. The doc's "Critical boundary" paragraph (§6, line 115) is incomplete.**
- **Bypass mechanism:** it says the experiment bypasses plan binding with empty `required_inputs`. The actual mechanism is the `c0-a2:` key prefix, because `bind_preparation_result` returns early unless the key starts with `prepare:` (`preparation_proof.py:114-117`). Empty inputs would pass `_references(())` for v1 anyway.
- **Unbound inputs:** `publish` doesn't bind or check the following (`c0_atomic_acceptance_prototype.py:56-63`, `:82-91`):
  - upstream refs, the workset, or the roots
  - `StageResult.status`, `input_refs`, or configuration/code versions against the identity
  - attempt against claim (`require_claim_publication` checks execution only, `claim_store.py:86`)
- **Replay:** a replay is "equal" on digest and size alone, so a replay with a different status or limitations is treated as identical.
- **Batch vs single transition (design inconsistency):** `StageIdentity` takes exactly one transition (`:83-92`, `:122-123`). The receipt requires exactly one batch result for the whole ordered set (`:253-271`). The batch-level identity is unspecified. List it as open.
- **Naming drift:** `stage_kind` values (`extracted`, `parsed`, `normalized`, `c0_contract_prototype.py:82-93`) differ from the doc §2 kinds (`extracted_components`, `parsed_parts`, `normalized_content`). `publish` requires `result.kind == stage_kind` (`c0_atomic_acceptance_prototype.py:58`). Any kind/version pairing is accepted, including `prepared@1`.

**P1-5. Overclaim in doc line 30.** "Malformed candidate rejected" is not what the native test shows.
- The test's `wrong` selection (`test_c0_native_a1_exact_handoff.py:102-111`) is rejected by the "not in workset.selections" guard (`c0_contract_prototype.py:383`).
- The ordinal-mismatch, ambiguity and saved-selection-mismatch branches (`:411-415`) are never run.
- Fix: reword the claim, or add a case where the selection is in the workset but the ordinal hash is wrong.

## Your six questions

1. **Receipt@2: structural only, not verified against durable payloads.**
   - `validate_against` takes a caller-supplied workset and ref, with no store reads. It does not check that result refs exist, are acceptable or claim-bound, or that the declared status matches the stored `StageResult` (`:283-353`).
   - A forged receipt with fabricated refs, claiming COMPLETE for a workset with no held entries, passes. The doc admits this (line 130).
   - COMPLETE with `workset.held` non-empty is rejected by the prototype, and the tests cover it (`:318-320`, `:347-348`). Legacy does not enforce that (P1-1).
   - Held-only worksets need INCOMPLETE and no roots. The transition batch must match the frozen order exactly. Baseline roots use `baseline_sources` and `baseline_selections`, with no fake `ReleaseEntryRef` (`FrozenRoot` validator `:49-71`).
   - `receipt_digest` (`:356`) digests an unvalidated receipt. The receipt doesn't bind the held set.

2. **StageIdentity: the key is input-only and deterministic.**
   - It uses a domain tag plus canonical JSON, with frozen versions, ordered upstream, and duplicate checks (`:102-147`). Extra fields are forbidden.
   - Invalid or forged keys are still acceptable in four ways:
     - `FrozenRoot` is caller-constructible. The tests use fake digests (`test_c0_contract_prototype.py:152-159`), nothing requires `selected.result_id == "intake-selection:" + proof`, and role and ordinal are not cross-checked.
     - Upstream refs and the workset are not checked for durability or kind.
     - `scope_key` is an arbitrary digest.
     - The `AcceptedPayload` logical key is only length-checked, not hex-checked (`:161-164`).
   - "Occurrence" means two things: the ordinal within an entry (`:41`) and the workset index (`:222`).

3. **Research SQLite table: it does what the doc says, within the limits above.**
   - It does BEGIN IMMEDIATE, fences on the claim before and after, keeps first-writer `StageResult` and semantic bytes immutable, and rolls back on conflict.
   - The concurrency tests give no real evidence of overlap, because there is no start barrier (`test_c0_atomic_acceptance.py:212-215`, `:269-273`). Serialization is SQLite's property, not something the test shows.
   - The two owners use different claim keys. In production, a deterministic partition key would make the second owner fail with `ClaimUnavailableError` (`store.py:267-268`).
   - The row-exists path decodes the payload inside the write lock (`c0_atomic_acceptance_prototype.py:94-105`). A1 deliberately avoids this (`intake_records.py:92-94`; proof is loaded before the writer transaction in `intake_store.py:359-407`). With a 64 MiB cap (`c0_contract_prototype.py:156`) that risks lock hold and lease expiry. Record it as a pattern not to productionize.
   - `asyncio.to_thread` on `store._store` bypasses the facade's semaphore, drain and close accounting (`async_store.py:376-393`, `421-442`). Cancellation safety on this path is unproven.
   - The doc does not overclaim production A1 lineage. Lines 113-115 are explicit, apart from the gaps in P1-4.
