# 请求频率与限流核查

结论：两轮日志证实 arXiv、Semantic Scholar 持续返回 429，但不足以证明“本次请求过密导致持续封禁”。本次可见的首个请求已经被拒绝；更早的请求、其他进程及共享出口流量没有完整记录。应按访问受限处理，暂停自动重复检索，同时保留对原因的判断边界。

用户已要求采用更长间隔。本项目后续研究的默认最小请求间隔设为每个来源 30 秒。配置已准备为 [config.next-run.toml](config.next-run.toml)，尚未执行；这不是服务方承诺的解封等待时间。

## 核查范围和证据

核查 Topic 01 的两次检索、各自配置、重试代码和 HTTP 客户端。已核对 11 个相关源文件，仓库内容与当前安装的 research-pipeline 0.32.0 文件哈希一致。原始结果见 [request-frequency-audit.json](execution/request-frequency-audit.json)。

本轮没有向论文检索 API 发出新请求。重试行为用本地构造的响应和模拟时钟验证；没有网络请求或真实等待。官方规则通过公开文档核对。

日志采用 UTC+10，与命令记录的 UTC 时间对应。以下时间均为 2026-09-14 的 UTC+10，精度为秒。只有 arXiv 明确记录请求发出时刻；其他来源主要记录失败返回时刻，不能把两者混为一谈。

| Semantic Scholar | 1 秒 | 5 秒 | 3 + 3 | 6 次 429 |

| --- | --- | --- |

首轮末次 arXiv 请求与次轮首次请求相隔 186 秒，即 3 分 6 秒；次轮首次请求仍然得到 429。两轮检索进程之间实际空闲约 104.06 秒。持续限制与这些结果相容，但限制的作用对象、期限和触发原因均未证实。

Semantic Scholar 首轮的三个 429 记录在 10:10:39、10:10:40、10:10:42；次轮在 10:16:19、10:16:25、10:16:30。次轮间隔增大与 5 秒限速配置相符，但这些是响应/失败事件时刻，不是完整请求发出记录。

arXiv 实际间隔还受到响应延迟、超时及指数退避影响。提高配置最小间隔不等于每个实测间隔都会变长；这两轮不是受控实验，不能据此断言进一步降速一定有效或一定无效。

## 对“已经封锁”的判断

arXiv 公布的常规 API 规则是每三秒至多一次请求、单连接，且按使用者控制的所有机器合并计算。本次可见的请求间隔没有超过这个频率；其他进程和机器的合计流量未知。满足常规频率也不能证明既有访问限制已解除。[arXiv API 使用条款](https://info.arxiv.org/help/api/tou.html#rate-limits)

429 表示服务端施加请求限制，但 HTTP 标准不规定其计数方式或用户识别方式；它本身不能证明某个 IP 被长期封禁。需要原始响应说明、额度/重置标记或服务方确认，才能进一步区分原因。[RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)

因此，可确认“这些请求受到限制”，不能确认“这两轮造成了永久或长期封禁”。已存在的限制、共享身份/出口额度、服务容量与其他历史流量仍是待验证解释。本次未核实 Semantic Scholar 当前账户的具体配额。

OpenAlex 的主要错误是无效日期参数导致的 400；降低频率不能修复这些参数。缺少 scholarly 依赖与 HuggingFace 无匹配也不属于频率问题。DBLP 缺少原始响应证据，不能仅凭 JSON 错误认定被封。

## 已验证的重试问题

1. **Retry-After 可能被随机扰动缩短。** 通用重试器先取服务器等待值，再施加 ±25% 扰动。离线复现中，Retry-After: 60 被计算为等待 45 秒；测试刻意选择扰动下界。此结果证明实现缺陷，不证明前两轮实际收到过 60 秒响应头。
2. **不支持 HTTP 日期格式的 Retry-After。** 通用解析器返回空值；arXiv 的独立路径也只处理数字格式。HTTP 标准允许秒数和 HTTP 日期两种形式。[RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)
3. **400 等非暂时性错误仍被重复请求。** 离线验证 400 被执行三次；历史 OpenAlex 日志同样显示无效参数被重试。
4. **限速状态仅属于当前对象/进程。** 新建来源客户端会重新初始化限速器；没有跨进程共享配额或持久化冷却截止时间。这是实现限制，尚未证明此前发生了同源并发超限。
5. **日志不足以追溯服务端限制。** 未保留原始 Retry-After、额度重置字段、受限响应摘要及所有来源的请求发出时间。因此不能还原服务端要求等待多久，也不能确认是否被提前重试。

这些问题已补充到 [PIPELINE_ISSUES.md](../PIPELINE_ISSUES.md)。其中 Retry-After 缺陷只在离线实验确认，不能倒推为此前 429 的既定原因。

## 后续执行配置

[config.next-run.toml](config.next-run.toml) 将 arXiv 及各来源的最小间隔统一设为 30 秒。第一轮配置和第二轮配置均已保留，历史使用的 config.run.toml 未被覆盖。已通过当前安装版本的配置解析验证。

30 秒仅控制单个客户端的常规请求间隔；当前实现仍有硬编码重试、Retry-After 缺陷及跨进程协调缺口。应先解决这些条件，再安排有完整诊断信息的有限恢复检查。收到 429 时应遵守服务器要求的等待时间；随机扰动不能使等待早于该时间。对于明确的参数错误应先修正请求。

本项目同时只运行一个研究流水线任务。后续主题继承这一保守配置要求；共享 Skill 的全局默认值调整列入后续改进工作。本轮没有修改共享 Skill/CLI 代码，也没有启动第三轮检索。
